Сервер — FastAPI-мост к поисковой логике бота: трекеры, каталог Кинопоиска,
карточки, серии и отдача `.torrent`. **Управления TorBox в нём нет, и ключ
TorBox ему не передаётся.** Это правило файла, и оно не меняется.

- Версия контракта: `1.3` (поле `version` у `/health`). 1.3 добавила
  необязательное `released: false` у невышедшего сезона в
  `/catalog/title/{kp_id}` и у его серий в `/catalog/{kp_id}/episodes`
  (см. «Какой сезон не вышел»). 1.2 добавила ленту «Что смотреть»:
  `/catalog/discover`, `/catalog/similar/{kp_id}`, `/catalog/briefs`.
  Прежние эндпоинты и поля не менялись.
- Авторизация: `Authorization: Bearer <SEARCH_API_TOKEN>` на всех эндпоинтах,
  кроме `/health`. Если на сервере токен пуст, проверка выключена — это режим
  разработки, не для VPS.
- Все ответы — JSON, кроме `/release/{id}/torrent`.

## Что нельзя ломать

Этим сервером пользуются три клиента: Telegram-бот (через общий модуль
`torbox_tg_bot`), выпущенное приложение TorBox One (`ios/`) и KinoApp.
TorBox One разбирает ответы через `Decodable` с необязательными полями, то
есть **новое поле он переживёт, а переименование или пропажу старого — нет**.
Набор старых полей `/search` заморожен тестом
`tests/test_search_api.py::SearchCompatibilityTests`.

## Проверка связи

### `GET /health`

Без токена. Ни одного обращения к внешним API — годится как проверка адреса
сервера на экране «Подключение».

```json
{
  "status": "ok",
  "version": "1.1",
  "token_required": true,
  "providers": ["NNM-Club", "Prowlarr"],
  "catalog": true
}
```

| Поле | Тип | Что значит |
|---|---|---|
| `status` | string | Всегда `ok`; сервер жив |
| `version` | string | Версия контракта |
| `token_required` | bool | На сервере задан `SEARCH_API_TOKEN` |
| `providers` | string[] | Настроенные источники поиска, человеческими именами |
| `catalog` | bool | Задан `KINOPOISK_API_KEY` |

`status` и `version` были и раньше; остальные поля добавлены.

### `GET /health/auth`

То же самое, но за токеном: так приложение проверяет не только адрес, но и
ключ, не тратя квоту каталога и не трогая трекеры.

```json
{"status": "ok", "version": "1.1"}
```

Неверный токен — `401` с телом `{"detail": "Неверный токен"}`.

## Поиск раздач

### `GET /search`

| Параметр | Тип | По умолчанию | Что делает |
|---|---|---|---|
| `q` | string | `""` | Свободная строка. Обрезается до 120 символов |
| `kp_id` | int | — | Идентификатор Кинопоиска: сервер строит запросы сам |
| `season` | int | — | Номер сезона; добавляет проход «имя сезон N» |
| `year` | int | — | Год; важнее года из каталога |
| `kind` | string | — | `movie` или `series`; иначе тип берётся из карточки |
| `limit` | int | `8` | Сколько раздач вернуть, максимум `40` |
| `deadline` | float | — | Срок в секундах. Без него сервер ждёт все источники, как раньше |

Нужен либо `q`, либо `kp_id`; иначе `400`. Ни одного настроенного источника —
`503`.

**Как строятся запросы.** Свободная строка идёт первой и одна — так работал
прежний вызов. По `kp_id` сервер собирает до трёх запросов:

- фильм: `«имя год»`, `«имя»`, `«оригинальное имя»`;
- сериал: `«имя сезон N»`, `«имя»`, `«оригинальное имя»`.

Запросов несколько не для полноты, а по необходимости: `title_matches_query`
требует, чтобы **все** слова запроса нашлись в имени раздачи, поэтому запрос
«имя год» в одиночку отсекает раздачи без года в названии. Году сериала в
запросе не место: четвёртый сезон вышел не в год премьеры сериала.

```json
{
  "status": {"NNM-Club": "18", "Prowlarr": "таймаут"},
  "partial": true,
  "sources": [
    {"name": "NNM-Club", "state": "ok", "found": 18},
    {"name": "Prowlarr", "state": "timeout", "found": 0}
  ],
  "results": [ { "...": "см. ниже" } ]
}
```

| Поле | Тип | Что значит |
|---|---|---|
| `status` | {string: string} | Имя источника → число найденных, `ошибка` или `таймаут` |
| `partial` | bool | **Новое.** Кто-то не успел к `deadline` |
| `sources` | object[] | **Новое.** То же, что `status`, но разбором |
| `results` | object[] | Раздачи |

`status` и `results` не изменились. `partial` всегда присутствует и равен
`false`, когда все источники ответили.

`sources[].state` — `ok`, `error` или `timeout`; `found` — сколько этот
источник отдал до отсева. **Пустая выдача не значит «ничего не нашлось»:**
если ни одного `ok`, отказали все источники, и клиент обязан сказать об этом
по-другому. Живая проверка 21.09.2026 попалась ровно на этом — оба трекера
отказали, а ответ выглядел как обычная пустая выдача. Разбирать ради этого
строки в `status` нельзя: там рядом лежат `"18"` и `"ошибка"`.

#### Строка выдачи

Первые тринадцать полей — прежние, их разбирает TorBox One:

| Поле | Тип | Что значит |
|---|---|---|
| `id` | string | **Изменилось:** теперь постоянный (см. ниже), а не uuid на час |
| `title` | string | Имя раздачи как на трекере |
| `size_text` | string | Размер строкой от источника |
| `size_bytes` | int | Размер в байтах; `0`, если источник не сказал |
| `seeders` | int | Раздающие |
| `leechers` | int | Качающие |
| `source_name` | string | Трекер: `NNM-Club`, `RuTracker.org`, … |
| `category` | string | Раздел трекера |
| `magnet_url` | string | Magnet или `""` |
| `info_hash` | string | Хэш, если источник его дал; **у NNM-Club всегда `""`** |
| `quality_summary` | string | «WEB-DL · 1080p · H.265» — строка для человека |
| `voiceover_summary` | string | «Дубляж · LostFilm» или «не указана источником» |
| `source_url` | string | Адрес темы |

Дальше — новые поля. Все они либо значение, либо `null`; `null` значит
«источник не сказал», и это не то же самое, что «нет».

| Поле | Тип | Что значит |
|---|---|---|
| `provider` | string | `nnm` или `prowlarr` |
| `score` | int | Серверный ранг: `score_release` + бонус источника + релевантность запросу |
| `content_kind` | string | `video`, `game`, `book`, `music`, `other` |
| `resolution` | int \| null | `2160`, `1080`, `720`, … |
| `source_type` | string \| null | `bdremux`, `remux`, `bluray`, `bdrip`, `web-dl`, `webrip`, `web`, `hdtv`, `hdrip`, `dvdrip`, `dvd`, `satrip`, `ts`, `camrip` |
| `video_codec` | string \| null | `av1`, `h265`, `h264`, `xvid`, `divx`, `mpeg2` |
| `hdr` | string \| null | `dolby_vision`, `hdr10plus`, `hdr10`, `hdr` |
| `voiceover_kinds` | string[] | `dub`, `multi`, `dual`, `single`, `author`, `professional`, `licensed`, `subtitles` |
| `voiceover_studios` | string[] | `LostFilm`, `Кравец`, `Кубик в Кубе`, … |
| `season_from`, `season_to` | int \| null | Границы сезонов из имени раздачи |
| `episode_from`, `episode_to` | int \| null | Границы серий |
| `episodes_declared` | int \| null | Объявленное число серий («1-8 **из 10**») |
| `published_at` | string \| null | Дата от индексера как есть (ISO-8601). У NNM-Club — `null` |

**Ранжирования под «цель 1080p» сервер не делает.** `score` — это ранг бота:
сиды, качество по словам в названии, доверие к трекеру, совпадение с запросом.
Поправки на кэш TorBox, битрейт под сеть и уже привязанного релизёра считает
клиент: сервер про TorBox ничего не знает и знать не должен.

#### Постоянные идентификаторы

| Источник | Форма | Пример |
|---|---|---|
| NNM-Club | `nnm:<номер темы>` | `nnm:1234567` |
| Prowlarr | `prowlarr:<индексер>:<хэш адреса темы>` | `prowlarr:rutracker-org:3f2a1c9d8e7b6a50` |

Проверено живьём: два одинаковых поиска подряд дали полностью совпадающий
набор id. У настроенных индексеров RuTor и BigFANGroup `source_url` заполнен
настоящими адресами тем, так что основа id есть. **Живьём не проверено**, что
будет через месяцы: если индексер сменит схему адресов, привязки протухнут.

Идентификатор не меняется между поисками, поэтому его можно хранить в базе
телефона рядом с тайтлом. Раньше это был `uuid4().hex` с жизнью час в памяти
процесса — сохранённая привязка «тайтл → раздача» превращалась в `404`.

У Prowlarr берётся не поле `id` из выдачи (оно считается от `guid` и между
версиями меняется), а адрес темы: `commentUrl` → `infoUrl` → `guid`.

Прежние uuid-идентификаторы из уже выданных ответов продолжают работать, пока
не кончится их час.

### `POST /release/hashes`

NNM-Club не отдаёт в выдаче ни magnet, ни `info_hash` — а это большинство
русских раздач. Без хэша приложение не может спросить TorBox, лежит ли
раздача в кэше. Считать хэш на каждом поиске нельзя: это по одному запросу к
трекеру на каждую раздачу. Поэтому — отдельный ленивый эндпоинт по верхним
кандидатам.

```json
{"ids": ["nnm:1234567", "nnm:1234568"], "limit": 12, "deadline": 25}
```

| Поле | Тип | По умолчанию | Что делает |
|---|---|---|---|
| `ids` | string[] | — | Идентификаторы из выдачи `/search` |
| `limit` | int | `12` | Сколько обработать, максимум `24` |
| `deadline` | float | `25` | Общий срок на всю пачку, в секундах |

```json
{"hashes": {"nnm:1234567": "a1b2c3d4e5f60718293a4b5c6d7e8f9012345678", "nnm:1234568": null}, "limit": 12}
```

Проверено живьём: четыре раздачи за 2485 мс, три хэша посчитаны по
`.torrent` NNM-Club, четвёртый пришёл от индексера. Перекрёстная проверка
сошлась — объявленный индексером хэш совпал с `sha1` от info-словаря
скачанного файла.

- Хэш — сорок символов в нижнем регистре, ровно как ждёт `checkcached` TorBox.
- `null` — посчитать не вышло: трекер не ответил, не успели к сроку или релиз
  по этому id не нашёлся. Это не ошибка запроса.
- Идентификаторов сверх `limit` в ответе нет вовсе. Сколько взяли — видно по
  полю `limit`.
- Хэш берётся из magnet или поля индексера, если они есть; иначе скачивается
  `.torrent` и считается `sha1(bencode(info))`. Хэш, пришедший с самим
  релизом, главнее кэша: он из той же выдачи, что и файл.
- Хэш описывает ровно тот файл, который сейчас отдаст
  `/release/{id}/torrent`. Поэтому он кэшируется на сутки **под файлом, а не
  под id**: ключ `hash:<id>:<файл>`, где файл у NNM-Club — номер вложения
  (`download.php?id=`), у Prowlarr — guid индексера. Кэш переживает
  перезапуск.
- Зачем так: онгоинг обновляется в той же теме новым `.torrent`, id
  `nnm:<тема>` остаётся прежним, а хэш меняется. До 23.09.2026 кэш под одним
  id сутки отдавал хэш прежнего файла. KinoApp находил раздачу «в кэше TorBox»
  и ждал файлы, а TorBox получал уже новый `.torrent` — «TorBox принял
  раздачу, но файлы так и не появились». Новое вложение получает свой хэш
  сразу.
- **Неудачи не кэшируются** — иначе разовый сбой трекера держался бы сутки.
- Отказ одного релиза не влияет на остальные.

### `GET /release/{id}/details`

Разбор темы на трекере. Форма не менялась.

```json
{
  "details_text": "Перевод: Дубляж\nВидео: MPEG-4 AVC, 1920x1080",
  "quality_summary": "WEB-DL · 1080p · H.265",
  "voiceover_summary": "Дубляж · LostFilm",
  "audio_summary": "AC3, 6 ch, 448 kbps"
}
```

### `GET /release/{id}/torrent`

Файл `.torrent`, `Content-Type: application/x-bittorrent`.

Порядок поиска релиза по идентификатору:

1. кэш в памяти (час);
2. дисковое хранилище (30 дней, переживает перезапуск);
3. для `nnm:<тема>` — перезапрос темы у трекера.

Шаг 3 проверен живьём в самом жёстком виде: экземпляр погашен, хранилище и
кэш хэшей удалены, экземпляр поднят заново — `/release/nnm:1201971/details`
вернул полный разбор за 1271 мс. Ссылка на `.torrent` живёт под номером
вложения, не темы, поэтому страницу и приходится читать. **На странице есть
magnet**, и хэш восстановленного релиза достаётся из него бесплатно: тот же
релиз отдал хэш за 970 мс без закачки файла, и хэш совпал с посчитанным по
`.torrent`. Записанная вычищенная страница — `tests/fixtures/nnm-topic.html`.

Восстановление релиза **Prowlarr живьём не проверено**: такие релизы живут
только в дисковом хранилище.

Раньше промах кэша означал `404`. Теперь `404` остаётся только там, где
восстановить нечего: **релиз Prowlarr, которого уже нет в хранилище**. Запроса
«отдай релиз по guid» у Prowlarr нет, и придумывать его неоткуда — в этом
случае клиенту надо повторить поиск.

## Каталог

Квота бесплатного ключа Кинопоиска — **500 запросов в сутки** и 25 запросов в
секунду (у фильтра и премьер — 5 в секунду). Проверено живьём: `accountType`
у ключа `FREE`, `dailyQuota.value` равен `500`, а `totalQuota.value` приходит
`-1` — это «без общего лимита», а не ошибка. Поэтому всё каталожное
кэшируется: карточки и справочники на 30 дней, полки на 12 часов, состав
сезонов идущего сериала — сутки (см. «Как долго сервер держит сезоны»).

Ошибки лимита отделены от «каталог недоступен»:

| Код | Когда |
|---|---|
| `429` | Суточная квота (у Кинопоиска это `402`) или запросы в секунду (`429`) |
| `502` | Каталог не ответил или ответил мусором |
| `503` | `KINOPOISK_API_KEY` не настроен |

### `GET /catalog/quota`

Остаток квоты ключа — бесплатный способ узнать её **до** платных вызовов.
Ответ отдаётся как есть от Кинопоиска: `totalQuota {value, used}`,
`dailyQuota {value, used}`, `accountType`. Без кэша, иначе цифра врёт.

### `GET /catalog/title/{kp_id}`

Живой ответ для «Джентльменов», 28.09.2026 (`meta` сокращён):

```json
{
  "meta": {"...": "TitleMeta, поля как у /meta/match",
           "tmdb_id": 236235, "tmdb_media_type": "tv", "seasons_count": 3},
  "imdb_id": "tt13210838",
  "seasons": [{"season": 1, "episodes": 8}, {"season": 2, "episodes": 8},
              {"season": 3, "episodes": 8, "released": false}]
}
```

- `meta` — тот же `TitleMeta`, что у `/meta/match`. Ловушка оттуда же:
  **`year` и `rating` — строки**, а не числа. Живьём подтверждено и добавилось
  ещё: у сериала **`duration_minutes` равен нулю** — Кинопоиск не отдаёт
  `filmLength` для `TV_SERIES` (у фильма пришло `169`).
- `tmdb_id` и `tmdb_media_type` — **внутри `meta`**, рядом с ним их нет.
  Кинопоиск их не отдаёт ни одним эндпоинтом; сервер выясняет их у самого
  TMDB по IMDb-идентификатору — точным редиректом, без ключа API. Не нашлось
  — `null`.
- `imdb_id` — из `v2.2/films/{id}`, там он есть.
- `seasons` — из `v2.2/films/{id}/seasons`; у фильма список пуст.
- `released` — **с версии 1.3**, необязательное: `false`, если сезон ещё не
  вышел (см. «Какой сезон не вышел»). У вышедшего сезона и там, где судить
  не по чему, **поля нет вовсе** — `true` сервер не отдаёт. `seasons_count` и
  `episodes` пометка не меняет: сезон-заглушка в них учтён, как и прежде.

Цена: 3 запроса к Кинопоиску (карточка, состав, сезоны) при первом открытии,
дальше — 0 в течение 30 дней. У идущего сериала сезоны перечитываются раз в
сутки — 1 запрос, если тайтл в эти сутки открывали. Пометка `released` к
этому ничего не добавляет: она считается из уже прочитанного.

### `GET /catalog/shelf/{kind}?page=1`

Карточки той же формы, что у `/catalog/popular` — приложение разбирает их
одним типом.

Полки из подборок Кинопоиска (`v2.2/films/collections`, до 50 страниц):

| `kind` | Подборка |
|---|---|
| `popular` | `TOP_POPULAR_ALL` |
| `popular_movies` | `TOP_POPULAR_MOVIES` |
| `popular_series` | `POPULAR_SERIES` |
| `top`, `top_movies` | `TOP_250_MOVIES` |
| `top_series` | `TOP_250_TV_SHOWS` |
| `top_xxi` | `TOP_100_GREATEST_MOVIES_XXI` |
| `closest_releases` | `CLOSES_RELEASES` |
| `family`, `comics`, `vampires`, `zombies`, `catastrophe`, `love`, `kids_animation`, `programmers`, `oscar_2021` | тематические |

Остальные:

| `kind` | Откуда |
|---|---|
| `premieres` | `v2.2/films/premieres` за текущий месяц; пагинации у этого эндпоинта нет |
| `genre/<название>` | `v2.2/films?genres=<id>&order=RATING`; id жанра берётся из `v2.2/films/filters` |
| `year/<год>` | `v2.2/films?yearFrom=&yearTo=&order=RATING` |

Неизвестный `kind` или незнакомый каталогу жанр — `404` с объяснением.

Живьём проверены `popular`, `top_movies`, `top_series`, `premieres`,
`genre/драма`, `year/1999`. `year` и `rating` сервер приводит к строке на
каждой полке, даже там, где Кинопоиск отдаёт число. У премьер рейтинга нет
вовсе (`""`), а `media_type` приходит `UNKNOWN`: эндпоинт премьер поля типа
не отдаёт. В полке по году встретился `media_type: "VIDEO"` — список значений
не закрыт.

**Чего у API нет и чего в полках не будет:**

- **отдельного «топа» эндпоинтом** — `v2.2/films/top` из документации убран,
  его заменили подборки;
- **«ожидаемого»** — это был `TOP_AWAIT_FILMS` того же убранного эндпоинта, в
  подборках замены нет;
- **«сейчас в кино»** — ближайшее `closest_releases`, но это «ближайшие
  релизы», а не «идёт в прокате»;
- **цифровых релизов** (что вышло на стримингах) — `v2.1/films/releases`
  удалён;
- **мультижанрового фильтра** — API принимает не больше одного жанра и одной
  страны за раз;
- глубины: по документации фильтр отдаёт не больше 400 карточек (20 страниц
  по 20), а **живьём 23.09.2026 — не больше 100**: `total: 100`,
  `totalPages: 5` на каждом из десяти разных запросов.

### Лента «Что смотреть» (версия 1.2)

Три эндпоинта для ленты рекомендаций KinoApp. Подбирать и ранжировать
приложение будет само: библиотека и история просмотра живут в телефоне, а
сервер отдаёт кирпичи — подбор по фильтру, «похожие» и карточки для показа.

Все три отдают **расширенную карточку**. Её первые десять полей — ровно
форма `/catalog/popular` и полок, дальше новые:

```json
{"catalog_id": 796660, "name": "Лучше звоните Солу", "original_name": "Better Call Saul",
 "media_type": "TV_SERIES", "year": "2015", "rating": "8.5", "countries": ["США"],
 "genres": ["драма", "криминал"], "poster_url": "https://…", "search_query": "Лучше звоните Солу 2015",
 "rating_imdb": "9.0", "votes": 237932,
 "tagline": "Честный адвокат превращается в ушлого решалу. Спин-офф «Во все тяжкие», который оказался не хуже оригинала",
 "overview": "История об испытаниях и невзгодах…", "backdrop_url": "https://avatars.mds.yandex.net/…",
 "logo_url": "https://avatars.mds.yandex.net/…", "duration_minutes": 0, "detailed": true}
```

| Поле | Откуда | Пусто значит |
|---|---|---|
| `rating_imdb` | элемент выдачи (`ratingImdb`, в подборках — `ratingImbd` с опечаткой) | оценки нет. **Строка**, как `rating` |
| `votes` | карточка фильма, `ratingKinopoiskVoteCount` | `0` — не спрашивали или нет |
| `tagline` | `shortDescription` — редакционное «о чём» в одну-две фразы | нет у тайтла |
| `overview` | `description` | нет у тайтла |
| `backdrop_url` | `coverUrl` — **квадратный** арт без надписей, оригиналом 3000×3000 и 2.6 МБ; CDN отдаёт уменьшенные по хвосту `/1920x1080` (1080×1080) | нет у тайтла |
| `logo_url` | `logoUrl` | нет у тайтла |
| `duration_minutes` | `filmLength` | `0` — неизвестно (у сериалов всегда) |
| `detailed` | пришла ли карточка фильма `v2.2/films/{id}` | `false` — все поля выше, кроме `rating_imdb`, **не спрашивались**, а не пустые |

Живьём у свежих тайтлов **обложки и логотипа чаще нет**: у «Проекта „Конец
света“», F1, «Питта» и «Сёгуна» есть `tagline`, но пусты `backdrop_url` и
`logo_url` — после 2022 года их нет на платформе Кинопоиска. У классики
(«Декстер», «Фарго», «Сопрано», «Крёстный отец») есть всё. У «Озарка» нет
ни обложки, ни логотипа, ни `tagline`.

#### `GET /catalog/discover`

Фильтр `v2.2/films` с параметрами:

| Параметр | Значения | По умолчанию |
|---|---|---|
| `type` | `ALL`, `FILM`, `TV_SERIES`, `MINI_SERIES`, `TV_SHOW` | `ALL` |
| `genre` | жанр по-русски, как в карточке | любой |
| `country` | страна по-русски, как в карточке: «США», «Корея Южная» | любая |
| `year_from`, `year_to` | год | без границы |
| `rating_from` | порог оценки Кинопоиска, дробный: `7.5` | без порога |
| `order` | `NUM_VOTE`, `RATING`, `YEAR` | **`NUM_VOTE`** |
| `page` | 1…20 (живьём страниц 5) | 1 |

Незнакомые тип, порядок, жанр или страна — `404` с объяснением:
`{"detail": "Каталог не знает страны «Атлантида»"}`. Кэш — тот же, что у
полок, 12 часов, ключ — сами параметры запроса. Полей карточки фильма здесь
нет: `detailed: false`.

Почему по умолчанию по голосам, а не по оценке, и почему страна —
главный рычаг (живьём 23.09.2026):

- **Сортировка по оценке без порога голосов — мусор.** Первые двадцать
  фильмов 2025–2026 по оценке: короткометражки, «фильмы о фильме»,
  спортивная документалка с оценками 8.6–9.5. По голосам сверху то, что
  действительно смотрели.
- **Без страны верх новинок — российский.** Все двадцать сериалов 2024–2026
  на первой странице по голосам — российские; фильмов 2025–2026 — тринадцать
  из двадцати. С `country=США` первая страница сериалов — «Фоллаут»,
  «Гангстерленд», «Сёгун», «Питт», «Рыцарь Семи Королевств».
- **Оценка IMDb отделяет проходное.** У «Мастера» 7.0 на Кинопоиске и 5.7 на
  IMDb, у «Иллюзии обмана 3» — 7.1 и 5.9. Поэтому `rating_imdb` и отдаётся.

#### `GET /catalog/similar/{kp_id}?limit=12`

«Похожие» Кинопоиска (`v2.2/films/{id}/similars`), и **каждый дополнен
карточкой фильма**: у самих «похожих» в элементе только id, названия и
постер — ни страны, ни жанров, ни оценки, а без страны приложение не может
отсеять то, чего не показывает. `limit` — сколько первых взять, 1…20, по
умолчанию 12. Порядок — порядок каталога.

- Список «похожих» кэшируется на 30 дней, карточки фильмов — там же, где их
  кэширует страница тайтла, тоже на 30 дней.
- Карточки идут параллельно, в четыре потока. Квота, кончившаяся посреди
  пачки, её не роняет: похожий без карточки остаётся с `detailed: false` и
  пустыми `countries`. `429` — только если не пришло вообще ничего.
- Незнакомый каталогу id — `200` и `[]`.

Живьём у «Во все тяжкие»: «Выстрел в пустоту», «Декстер», «Далласский клуб
покупателей», «Фарго», «Лучше звоните Солу», «Сопрано», «Дурман»… Фильмы и
сериалы вперемешку — делить их по виду приложению.

### `GET /catalog/{kp_id}/episodes?season=N`

То же, что `GET /meta/{film_id}/episodes`. Старый путь остаётся и работает.

```json
[{"season": 1, "episode": 1, "title": "Зима близко", "overview": "…", "air_date": "2011-04-17", "still_url": "https://image.tmdb.org/…"}]
```

Кадров серий у Кинопоиска нет: `still_url` заполняется из TMDB и только при
заданном `TMDB_API_KEY`, иначе — пустая строка.

С версии 1.3 у каждой серии невышедшего сезона — `released: false`, по тому
же правилу, что у сезона в `/catalog/title` (см. «Какой сезон не вышел»). У
серий вышедших сезонов поля нет. Живьём 28.09.2026, «Джентльмены»:

```json
[{"season": 2, "episode": 8, "title": "Episode #2.8", "overview": "", "air_date": "2026-09-03", "still_url": "https://image.tmdb.org/t/p/w780/…"},
 {"season": 3, "episode": 1, "title": "Episode #3.1", "overview": "", "air_date": "2026-09-03", "still_url": "", "released": false},
 {"season": 3, "episode": 2, "title": "Episode #3.2", "overview": "", "air_date": "", "still_url": "", "released": false}]
```

#### Как долго сервер держит сезоны

Состав сезонов (`v2.2/films/{id}/seasons`) — один ответ на весь сериал,
общий для `/catalog/title` и серий. Срок у него зависит от содержимого и
решается при чтении:

- **сутки**, если последний сезон идёт: у него нет серий или есть серия без
  даты, с датой в будущем, вышедшая за последние 28 дней либо с
  датой-заглушкой — 1 января у двух и больше серий сезона;
- **30 дней**, как у карточки, если последний сезон завершён.

Записи, положенные прежней версией на 30 дней, оцениваются так же, при
чтении. Если перечитать не вышло (квота, сеть), отдаётся прежний состав, а
не пустой. Карточку и серии KinoApp спрашивает в одну секунду; перечитывает
их один поток, так что это один запрос к Кинопоиску, а не два.

Живьём 23.09.2026, «Тед Лассо» (`kp 1309707`): у всех десяти серий 4 сезона
дата `2026-01-01` и имена `Episode #4.N`, русских имён нет. Запись в кэше
была суточной давности и совпала с ответом Кинопоиска, запрошенным тогда же:
**заглушки отдаёт сам Кинопоиск**, а не месячный снимок. По TMDB серии
выходят еженедельно с 4 августа 2026, к 23.09 вышло восемь. Суточный срок
этого не исправит, но и не заморозит на месяц исправление Кинопоиска.

#### Какой сезон не вышел

С версии 1.3. Правило одной фразой: **сезон не вышел, если у сериала есть
TMDB и TMDB этого сезона не знает или ставит ему дату позже сегодняшней, а у
Кинопоиска в этом сезоне не больше одной серии с прошедшей датой.** Тогда у
сезона в `/catalog/title` и у каждой его серии в `/catalog/{kp_id}/episodes`
(и в старом `/meta/{film_id}/episodes`) — `released: false`. Иначе поля нет.

- «Есть TMDB» — сериал нашёлся точным редиректом по IMDb-идентификатору,
  тем же, что даёт `meta.tmdb_id`. Нечёткий поиск по названию — запасной
  путь кадров серий — правилу не годится: чужой сериал с другим числом
  сезонов пометил бы вышедший сезон. Без `TMDB_API_KEY` поля нет: список
  сезонов TMDB отдаёт только с ключом.
- «TMDB не знает сезона» — его нет в `seasons` ответа `GET /3/tv/{id}` или у
  него `air_date: null`. `air_date` — дата первой серии сезона; сезон, у
  которого она сегодня, уже вышел.
- «Серия с прошедшей датой» — `releaseDate` Кинопоиска не позже сегодняшнего
  дня по часам сервера (UTC). Одну такую серию правило терпит: сезон-заглушка
  Кинопоиска копирует в первую серию дату прошлого сезона.
- Половина про Кинопоиск держит от ложных пометок при другой нумерации
  сезонов у TMDB (например, когда там все серии в одном сезоне): у вышедшего
  сезона у Кинопоиска серии с датами. Это проверено тестом на придуманных
  данных, а не живьём — в кэше сервера такого сериала не нашлось.

Живьём 28.09.2026, «Джентльмены» (`kp 1435343`, TMDB `236235`): у Кинопоиска
3 сезон — восемь серий `Episode #3.N`, дата только у первой (`2026-09-03`,
как у всех серий 2 сезона), кадров нет. У TMDB два сезона, `2024-03-07` и
`2026-09-03`, `status: "Returning Series"`, `next_episode_to_air: null`:
Netflix продлил сериал в августе 2026, даты 3 сезона нет. До 1.3 приложение
считало 3 сезон вышедшим и после S2E8 искало раздачи S3E1, которых нет.

Прогон правила по кэшу боевого сервера 28.09.2026: 9 сериалов с сезонами,
помечен один сезон — 3 сезон «Джентльменов». Сезон-кандидат (не больше одной
серии с прошедшей датой у Кинопоиска) нашёлся только там; остальным восьми
TMDB даже не понадобился. У «Теда Лассо» 4 сезон идёт (у TMDB с 04.08.2026),
а у Кинопоиска все десять его серий с заглушкой `2026-01-01` — это прошедшая
дата, и пометки нет.

Откуда даты и сколько это стоит:

- `GET /3/tv/{id}` — один запрос на сериал: в ответе весь список `seasons` с
  `season_number` и `air_date`. Запись `tmdb-seasons:{kp_id}` в
  `META_CACHE_PATH` живёт 30 дней, как карточка; запись, по которой хоть один
  сезон не вышел, перепроверяется раз в сутки — иначе снимок, взятый до того,
  как TMDB завёл новый сезон, прятал бы вышедшую первую серию до второй. Не
  вышло перечитать — прежняя запись живёт ещё сутки.
- TMDB спрашивается, только если у Кинопоиска есть сезон-кандидат; вышедшим
  сериалам правило не стоит ни одного запроса.
- Редирект по IMDb — один на тайтл, общий с кадрами серий
  (`tmdb-imdb:{kp_id}`): найденный id живёт 30 дней, промах — сутки.
- **Запросов к Кинопоиску правило не добавляет**: состав сезонов и карточка
  уже в кэше. Пометка считается при каждом ответе, а не хранится в карточке,
  поэтому у тайтлов, положенных в кэш до 1.3, она появилась без сброса кэша.

**Живьём не проверено:** TMDB, который не отвечает (сезоны тогда без
пометки, как до 1.3), и сезон, который TMDB ведёт без даты, — в кэше такого
не было, `air_date: null` пришёл только у спецвыпусков (сезон 0) сериала
«BBC: Планеты».

## Сколько это стоит в запросах к Кинопоиску

Квота — 500 в сутки. На холодном кэше:

| Действие | Запросов | Потом |
|---|---|---|
| Главный экран с N полками | N (по одному на полку) | 0 в течение 12 часов |
| Полка по жанру, впервые | 2 (справочник жанров + фильтр) | 1 на полку, справочник живёт 30 дней |
| Открыть страницу тайтла | 3 (карточка, состав, сезоны) | 0 в течение 30 дней; у идущего сериала — 1 в сутки (сезоны) |
| Серии сезона | 0 (сезоны уже в кэше от карточки) | 0; у идущего сериала — тот же 1 в сутки |
| «Смотреть» по `kp_id` | 0 (карточка уже в кэше) | 0 |
| Поиск по трекерам | 0 — каталог тут не участвует | 0 |
| `discover`, первый с жанром или страной | 2 (справочник + фильтр) | 1 на запрос, справочник живёт 30 дней |
| `discover` | 1 | 0 в течение 12 часов |
| `similar`, `limit=N` | 1 + N (список + карточки) | 0 в течение 30 дней; карточки общие со страницей тайтла |
| `briefs`, N id | N | 0 в течение 30 дней |

Главный экран с шестью полками — 6 запросов, и следующие 12 часов он
бесплатен. Открытие ста разных тайтлов за сутки — 300 запросов. Проверить
остаток можно `GET /catalog/quota`, он квоту не тратит.

**Цена суточного срока сезонов.** Лишний запрос — один в сутки на идущий
сериал, и только если его в эти сутки открыли: карточка, серии или
«Смотреть» по `kp_id`. Замер по кэшу и журналу сервера 23.09.2026: в кэше 9
сериалов, правило пометило идущими 3 («Тед Лассо», «Джентльмены», «Холод»);
за 21–23.09 открывали по 1–2 идущих в сутки, то есть 1–2 запроса из 500,
меньше 0,5 %. Потолок — число разных идущих сериалов, открытых за сутки:
двадцать таких — 20 запросов, 4 % квоты. Для масштаба: днём 23.09 из
квоты было израсходовано 242 запроса.

**Пометка невышедшего сезона (1.3) квоту не тратит**: она считается из уже
прочитанных сезонов и карточки. Спрашивает она только TMDB, у которого
суточной квоты нет, — один запрос `/3/tv/{id}` на сериал с сезоном-кандидатом
раз в 30 дней, а пока сезон помечен — раз в сутки.

| Переменная | По умолчанию | Зачем |

### Как это развёрнуто на самом деле

Приведено в соответствие 21.09.2026: `torbox-search-api.service` и
`nginx.search-api.conf` в репозитории теперь описывают работающую установку
(домен и адрес в примере заменены заглушками). `Caddyfile.search-api`
оставлен как вариант для тех, у кого Caddy, но на сервере его нет.

| | Как в репозитории было | Как работает |
|---|---|---|

| | В репозитории | На сервере |
|---|---|---|
| Рабочий каталог | `/opt/torbox-telegram-bot` | `/opt/torbox-one` |
| Окружение | `/etc/torbox-telegram-bot.env` | **отдельный** `/etc/torbox-search-api.env` |
| Порт | `8787` | `18787` |
| Наружу | Caddy | **nginx**, отдельный сайт, HTTPS |
| Python | не оговорён | **3.10.12** — это и есть минимум |

Бот живёт в своей папке, со своей копией `torbox_tg_bot.py` и своим venv, и
на выкладку сервера поиска не реагирует вовсе. Его код в этот репозиторий
не входит: он развился в отдельную линию публичного бота и лежит в ветке
`sync/prod-bot-20260921`.

Рабочая папка сервера поиска — клон этого репозитория. Выкладка кладёт
файлы поверх клона, поэтому его `git status` показывает изменения: это
ожидаемо и чинится переключением на ветку, когда она попадёт на GitHub.

**Минимальная версия Python — 3.10.** Код это выдерживает: `X | None` в
аннотациях на 3.10 работает, `match`, `tomllib`, `Self`, `TaskGroup` и
`ExceptionGroup` не используются. Одна ловушка уже поймана: до 3.11
`concurrent.futures.TimeoutError` — отдельный класс, а не псевдоним
встроенного, и обработчик дедлайна пришлось импортировать явно.

**На VPS `SEARCH_API_STATE_DIR` обязателен.** Сервис живёт под `DynamicUser`
с `ProtectSystem=strict`, рабочий каталог `/opt/torbox-telegram-bot` у него
только для чтения, и без этой переменной ни один кэш не сохраняется — он
молча живёт в памяти до перезапуска. В `torbox-search-api.service` переменная
уже прописана на `StateDirectory`.

## Откуда сервер вообще достаёт источники

Замерено 21.09.2026 с двух машин. Это не про настройку, а про то, где сервер
способен работать: половина источников доступна не отовсюду.

| Источник | Домашний Mac | Московский VPS (Selectel) | Сервер бота |
|---|---|---|---|
| `nnmclub.to` | `403`, Cloudflare-челлендж | TLS-рукопожатие рвётся (`curl exit 35`) | **`200`** |
| `rutracker.org` | не проверялся | то же, `curl exit 35` | `301` |
| `kinopoiskapiunofficial.tech` | работает | работает | работает |
| `api.themoviedb.org` | работает | **не отвечает** | `301` |

Сервер, где живёт бот, достаёт всё. Две другие машины — нет, и по разным
причинам.

Два разных запрета, и ни один не лечится настройкой сервера:

- **С российского адреса трекеры закрыты по SNI.** TCP проходит, рукопожатие
  обрывается — подпись блокировки на магистрали, а не отказ сайта. Сервер
  поиска на VPS в РФ до трекеров не достучится, пока трафик не пойдёт через
  прокси.
- **С неросийского адреса трекер закрывает Cloudflare.** `cloudscraper`,
  которым ходит `NnmClient`, текущий челлендж не решает. Формы входа в ответе
  нет — это анти-бот, а не «нужен логин».
- **TMDB с российского адреса недоступен.** На VPS в РФ `tmdb_id` и кадры
  серий не заработают, даже если ключ задан: `still_url` останется пустым, а
  `tmdb_id` нулём. Кинопоиск оттуда доступен.

Вывод для выкладки: машине с сервером поиска нужен выход и к трекерам, и к
TMDB. Ни домашний Mac, ни московский VPS сами по себе такой пары не дают.
